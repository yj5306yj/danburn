# danburn start — 도급내역서로 품질관리계획서 새로 만들기

사용자가 맡기는 일: 도급내역서(xlsx) 하나와 몇 가지 답.
도구가 하는 일(`danburn start`): 내역서를 먼저 읽고 → 모호한 것만 묻고 → 법 판정(품질관리계획/품질시험계획, 배치 등급) → 현장 정보(project.yaml) → 계획서 → "확인할 것" 목록.
**이 스킬이 하는 일: 그 대화를 사용자에게 한 번에 한 질문씩 그대로 전하고 답을 넘긴다.** 질문·선택지·기본값은 도구가 정한다(`src/danburn/data/interview.yaml`). 스킬이 질문을 지어내거나 법 판정을 다시 계산하지 않는다.

사용자가 준 인자: `$ARGUMENTS` — 내역서 파일이나 폴더면 그 폴더를 `--folder` 로 쓰고, 도구가 내역서를 물으면 그 파일로 답한다. 비었으면 도구의 첫 질문(내역서)부터 그대로 전한다. 사용자가 hwp·hwpx·pdf **계획서**를 줬다면 새로 만들기가 아니라 검사다 — check 스킬(`/danburn:check <계획서>`)로 안내한다.

## 준비 — 실행 파일 `<danburn>` 찾기 (먼저 OS·셸 확인)
- 이 스킬은 **로컬 파일을 읽고 명령을 실행할 수 있는 에이전트**에서만 동작한다. 그런 도구가 없는 대화 창이면 처음에 그 사실을 알리고, 명령 실행이 되는 환경(CLI 에이전트 등)을 안내한다. 글만 읽고 설치됐다고 말하지 않는다.
- 아래 순서로 처음 되는 것 하나를 `<danburn>` 으로 쓴다. `<danburn> --help` 가 나오면 된다.
  0. **이미 설치됨** — `danburn --help` 가 되면 그대로 `danburn`(랜딩·README 의 `uv tool install git+https://github.com/yj5306yj/danburn` 으로 설치한 경우). 새 기준은 `uv tool upgrade danburn` 으로 받는다.
  1. **플러그인으로 설치됨** — 플러그인 폴더가 `${CLAUDE_PLUGIN_ROOT}` 이다(Claude Code 가 실제 경로로 바꿔 넣는다. 글자 그대로 `${…}` 로 보이면 플러그인이 아니니 건너뛴다). 설치된 플러그인 판과 같은 코드를 쓴다:
     `uvx --from "${CLAUDE_PLUGIN_ROOT}" danburn`
  2. **저장소 안** — `pyproject.toml` 과 `src/danburn/` 이 있는 폴더(`<저장소>`)에 가상환경이 있으면:
     맥·리눅스 `<저장소>/.venv/bin/danburn`, Windows `<저장소>\.venv\Scripts\danburn.exe`
  3. **둘 다 없음** — 공개 저장소에서 바로:
     `uvx --from git+https://github.com/yj5306yj/danburn danburn`
- 1·3 은 `uv` 가 필요하다. `uv --version` 이 안 되면 **여기서 멈추고** 사용자에게 한 줄 설치를 안내한 뒤 새 터미널에서 다시 하자고 한다:
  - 맥·리눅스: `curl -LsSf https://astral.sh/uv/install.sh | sh`
  - Windows(PowerShell): `powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"`
- 처음 `uvx` 실행은 파이썬과 의존성을 받느라 몇십 초 걸린다(다음부터는 캐시). 네트워크가 막혀 있으면 2(저장소 `.venv`)를 쓴다.
- 출력은 UTF-8 이다(파이프로 받아도 도구가 UTF-8 로 쓴다). 실행기에서 출력을 UTF-8 로 읽는다. `PYTHONIOENCODING` 을 cp949 로 넣지 않는다(넣으면 한글 기호에서 멈춘다). PowerShell 5.1 은 `&&` 를 못 쓴다 — 명령을 한 줄씩.

기본은 방법 B(에이전트가 중계)다. 사용자가 터미널에서 직접 답하겠다고 하면 방법 A.

## 방법 A — 사용자가 직접(가장 간단)
- 사용자에게 대화 창에서 `! <danburn> start` 를 치라고(`<danburn>` 은 위에서 찾은 실제 명령으로 바꿔서) 안내한다(또는 터미널에서 직접). 도구가 직접 묻는다.
- 한 줄로 알려 줄 것: "번호로 고르고, Enter 는 기본값, `-` 는 모름, `?` 는 도움말, 파일은 창에 끌어다 놓으면 됩니다."
- 끝나면 도구가 보여 준 **"확인할 것"** 을 같이 본다(아래 "끝나면").

## 방법 B — 에이전트가 중계 (한 줄 모드 `--plain`)
에이전트는 대화 사이에 입력을 기다리는 프로세스를 붙잡을 수 없다. 그래서 **지금까지의 답 목록을 입력으로 다시 돌려 다음 질문 한 줄까지 받는다**. 같은 답이면 같은 질문이 나온다.

1. 저장소 밖 임시 폴더에 **답 목록 파일** `answers.txt` 를 빈 파일로 만든다(파일 쓰기 도구로 — 셸 명령 불필요). 한 줄에 답 하나씩 UTF-8 로 쌓는다.
2. 매번 같은 명령을 실행한다(맥·Windows 공통, 셸 리다이렉션 `<` 없음). `--folder` 는 사용자의 내역서가 있는 폴더다:
   ```
   <danburn> start --plain --input "<임시 폴더>/answers.txt" --folder "<사용자 폴더>" --out-dir "<산출 폴더>"
   ```
   - `--input` 모드는 답 목록을 처음부터 다시 돌리므로 "이어서 할까요?" 초안이 끼어들지 않는다(환경변수 불필요).
   - 산출 폴더를 주지 않으면 `~/Documents/danburn/<공사명>/`(Windows 는 사용자 폴더의 `Documents\danburn\<공사명>\`) 이다. 저장소 안이면 도구가 거부한다.
3. 출력의 **마지막 대기 줄** 하나만 사용자에게 전한다. 종료 코드 2와 "멈춤: 입력이 끝났습니다"는 **다음 답을 기다린다는 뜻**이다(오류 아님). 대기 줄의 모양:
   - `Q<번호> <키> | 질문 | 1=… 2=… | 기본=…` — 질문과 선택지를 그대로 보여 준다. 사용자가 번호·글로 답하면 그 말 그대로 한 줄 더한다. 빈 줄 = 기본값(`기본=` 이 없는 질문은 빈 답을 받지 않는다), `-` = 모름.
   - `Q<번호> <키> | 내역서에서 '…'(으)로 읽었습니다. 맞나요? | Y=맞음 n=고치기` — 내역서에서 읽은 값 확인. `Y` 또는 `n` 을 더한다(n 이면 다음에 원래 질문이 나온다).
   - `READ …` — 도구가 내역서를 읽은 결과(동·분야·공사명·총액·발주자·행 수). 질문이 아니다. 한 번 요약해 보여 준다.
   - `JUDGE` 와 그 아래 줄들, 그리고 `맞나요? [Y/n]` — 판정 화면이다. **도구 출력 그대로** 보여 주고(계획 종류·근거 조문·배치 등급·시험실·인력 기준·승인 절차, `! 확인 필요` 줄) 맞으면 `Y`, 아니면 `n` 과 고칠 질문 번호(예: `4-2`)를 차례로 더한다.
   - `지금 계획서를 만들까요? [Y/n]` — `Y` 를 더하면 계획서를 만든다(몇 초 걸린다).
   - `SITE <n>` 다음 `Q확인 <키> | …` — 계획서를 만든 뒤 도구가 정하지 못한 내역(규칙 밖 행·설치 행·품명으로 알 수 없는 행). 한 개씩 전하고 번호를 더한다. Enter = 나중에.
   - `ASKED <m> CONFIRMED <n>` — "내역서를 읽고 n가지는 확인만, m가지를 물었다"는 뜻. 질문 아님.
   - 대기 줄 바로 위에 `다시 입력하세요` 가 있으면 **마지막 답이 거부된 것**이다(빈 답·없는 번호). 그 답을 목록에서 지우고 같은 질문을 사용자에게 다시 묻는다. 거부된 답을 남겨 두면 뒤의 답이 한 칸씩 밀린다.
4. 종료 코드 0이면 끝이다. 출력의 `계획서:`·`요약  :` 경로와 **"확인할 것"** 목록을 받는다. 종료 0 만 믿지 말고 그 경로의 `품질관리계획서.hwpx` 가 이번 실행에서 생겼는지 확인한다(사용자가 "지금 만들까요?"에 n 이면 계획서는 없다 — 생성 성공으로 보고하지 않는다).
5. 끝나면 임시 폴더를 지운다(답 목록에 사용자 경로가 들어 있다).

오류일 때(종료 코드와 첫 줄로 구분):
- `입력 오류: …`(종료 2) — 적힌 파일(내역서·현장 정보·답 파일)을 적힌 대로 고친 뒤 다시 실행. 사용자에게 그 파일을 다시 고르게 한다.
- `출력 파일을 바꾸지 못했습니다`(종료 2) — 한글에서 그 계획서를 열어 둔 경우다. 창을 닫고 다시 실행하라고 안내한다. 기존 파일은 그대로다.
- `그 파일은 계획서입니다` — 내역서 대신 계획서를 줬다. 새로 만들기에는 xlsx 가 필요하고, 그 파일은 `/danburn:check <계획서>`(check 스킬)로 검사할 수 있다고 안내한다.
- 종료 1(`예상하지 못한 오류`) — `DANBURN_DEBUG=1` 로 다시 실행한 출력을 이슈로 보고하도록 안내한다. 임의로 우회하지 않는다.

미리 답을 다 알면(자동화) 답을 yaml 로 모아 `danburn start --answers <파일>` 한 번으로 돌려도 된다. 키는 `src/danburn/data/interview.yaml` 의 `key` 다(예: `내역서`·`블록`·`발주자_구분`·`공사종류`·`총공사비_억원`·`연면적`·`지상층수`·`공사명`·`시공자`·`로고`, 현장 확인은 `현장_확인: {키: 예|아니오}`, 품명으로 알 수 없는 행은 `{"name:<품명>": 예|아니오|<종별 key>}`).

## 끝나면 — 사용자 말로 요약
- 첫 줄: 계획서 경로.
- 판정: 계획 종류와 배치 등급 한 줄. `확인 필요` 가 있으면 그 이유(어떤 답을 모르는지).
- "확인할 것" 을 차례대로 짧게 전한다:
  - 경고(발주처 기준 필요·규칙 없음·규칙 밖 행 등): 그 자재의 시험계획은 사람이 발주처 기준으로 써야 한다.
  - `(작성 필요)` 로 남긴 칸: 산출 폴더의 `project.yaml` 에서 적은 뒤 다시 만들면 된다(방법 B 를 이어 하거나 아래 `plan`).
  - 현장 확인을 "나중에"로 남긴 수.
- 초안이며 현장 조건(발주처 특기시방·감리 지시)은 **품질관리자가 확정**한다고 적는다. 한글(맥은 무료 한글 Viewer)에서 열어 확인하라고 안내한다.
- 더 자세한 항목은 산출 폴더의 `요약.json` 에 있다(`warnings`·`needs_confirmation`·`member_inferred`·`missing_common_specs` 등).

## 개인정보 — 도구의 규칙과 같게
- 내역서·로고·증빙 파일은 **사용자 컴퓨터 경로만** 쓴다. 파일을 복사·업로드·요약하지 않는다. 증빙(자격증·경력증명서)은 열지 않는다.
- 증빙 파일 이름·경로를 대화나 로그에 옮겨 적지 않는다. **개수만** 말한다("증빙 2건"). 도구도 화면·요약에 개수만 쓴다.
- 증빙을 넣겠다고 하면 "주민등록번호 뒷자리를 가렸는지" 한 번 확인한다. 지금은 계획서에 넣지 않고 목록만 남는다.
- project.yaml·계획서는 저장소 밖 산출 폴더에 둔다(도구가 강제). 답 목록 파일도 저장소 밖 임시 폴더에 두고 끝나면 지운다.
- "관급/사급"이라는 말로 발주자를 묻지 않는다(내역서의 지급/사급과 헷갈림). 도구 문구("발주자가 국가·지자체·공공기관인가요?")를 그대로 쓴다.

## 고급: 직접 명령
start 없이 명령으로 돌릴 때(개정·옵션 조정). `danburn` 은 위 준비에서 찾은 `<danburn>` 이다.
- `danburn check-basis` — 계산 기준(업무지침 고시)이 현행인지. 0=현행, 3=개정됨(사용자에게 알림), 4=확인 못 함.
- `danburn inspect --boq "<내역서>"` — 읽을 수 있는지(`supported`), 동(블록) 목록.
- `danburn plan --boq "<내역서>" --block "<동>" --project "<project.yaml>" --revision <N> --date "<YYYY. MM. DD.>" --out "<폴더>/품질관리계획서.hwpx"` — start 가 만든 project.yaml 을 고친 뒤 다시 만들 때.
  - `--revision`·`--date` 는 project.yaml `개정이력` 과 맞아야 한다(다르면 종료 2, 파일 안 만듦).
  - 요약을 보고 다시 돌리는 옵션:
    - `--owner LH`(LH 시험기준)
    - `--formwork-sets`(레미콘 부위 `member_inferred` 의 `confirm: true`)
    - `--makers`·`--non-ks`(철근 "제조사 수 확인")
    - `--add-spec`(`missing_common_specs`)
    - `--civil-scope 공구`
    - `--confirm key=예,…`(현장 확인)
    - `--include-optional`
    - `--offline`
- `danburn build …` — 8.11 표만(`--project` 없이).
- `hwpx-validate "<계획서>"` — 파일 구조 검사(`<danburn>` 옆의 같은 폴더에 있다. uvx 로 쓰면 `uvx --from <같은 출처> hwpx-validate`).
- 결과 `품질관리계획서.json` 은 8.11 행 목록이다(`item`·`test_type`·`qty`·`unit`·`frequency`·`calc_basis`·`count_site`·`count_external`·`count_ks`·`note`·`basis`). `calc_basis` 가 "KS자재"이고 횟수 0 이면 결함이 아니다(KS 제품 시험 면제, ◎ 표시).

## 한계
- 별표2 주요 자재 규칙과 LH 기준(`--owner LH`)만 계산한다. 나머지는 경고와 계획서 8.11 뒤 "시험계획 미작성 자재" 표로 알린다.
- 품질시험계획 대상이어도 문서는 품질관리계획서 구성(표지 제목만 "품질시험계획서")으로 나온다.
- 층·연장·일수 기준 빈도는 내역서로 셀 수 없어 최소 1회로 두고 비고에 조건을 적는다.

## 하지 말 것
- 질문을 새로 만들거나 도구의 판정·계산을 손으로 고쳐 "맞춰" 보고하지 않는다. 이상하면 그대로 보여 주고 답을 고쳐 다시 돌린다.
- 내역서·산출물을 외부 서비스에 올리지 않는다(네트워크는 기준 최신 확인의 공개 법령 조회뿐).
